Review discovery uses `owner.github`, independently of the CLI account's `@me` shorthand. It searches all open PRs assigned to, mentioning, or requesting the configured owner, plus review requests for the owner's teams. It deliberately ignores legacy `pr_review.updated_since` values. Repository scope, draft exclusion and self-review exclusion still apply; discovering an item does not authorize reviewing, merging or deploying it.

The read-only helper accepts merged config JSON on stdin and emits one complete candidate array. It paginates each search and team membership list. GitHub's 1,000-result search cap is handled by splitting creation-time ranges; incomplete, changing-length or unsplittable results fail discovery rather than silently dispatching a partial queue. Search indexing and concurrent GitHub changes still mean a subsequent run may discover additional items.

By default team discovery requires authenticating as the configured owner with permission to list their teams (normally `read:org`). For a different authentication identity, disable `pr_review.discover_teams` and explicitly configure every applicable `org/team` slug in `pr_review.teams`. An empty explicit list means no team requests will be searched in that mode.

Validate configuration without launching workers:

```bash
source bin/lib.sh
cfg -o=json '.' | bin/review-discovery
```

Deploy the scripts and config together after review, with the Hub alert adapter built and restarted as described below. Preserve existing pause state and scheduler state. A normal fleet tick also dispatches and babysits; enabling its scheduler is a separate operational decision. A review-only invocation uses `bin/fleet review-prs` and retains pause, capacity, budget and same-head gates. Obtain authorization before re-enabling automation stopped by an owner cancellation.

An opt-in review-only LaunchAgent template is provided at `launchd/com.llm-brain.reviews.plist`. It runs only `bin/fleet review-prs` every five minutes, with a separate `reviews.log`. Launchd serializes executions of this service; worker capacity and persisted same-head/budget-stop gates remain in the existing command. It does not refresh chat intake, dispatch issues or babysit PRs. Bootstrap does not install it automatically.

For recovery, first review and deploy the discovery code and the private scope configuration together. Set `pr_review.repo_regex: ".*"` in the private overlay if all repositories under the configured owners should be included. Validate discovery read-only and check authenticated-owner team permissions. Then, only with authorization to resume reviews, render the template's `__BRAIN__` and `__HOME__` placeholders to the deployment checkout and home directory, validate it with `plutil -lint`, and install it as `~/Library/LaunchAgents/com.llm-brain.reviews.plist`. Loading that service starts reviews immediately because `RunAtLoad` is true. Leave `com.llm-brain.fleet` unloaded; do not run the general bootstrap as part of this recovery. Preserve PAUSE/config pause settings; do not clear them to force a start. To stop review scheduling, boot out only `gui/<uid>/com.llm-brain.reviews`; already-running review workers need separate handling.

Durable metrics are stored privately in `$BRAIN_STATE/review-health.json` under an advisory file lock and atomic replacement. `bin/fleet review-status` prints the summary without GitHub or model calls. The discovered count is the deduplicated GitHub/chat candidate union; eligible applies scope, draft and self-review gates. Queued, running, failed, blocked and missing describe each eligible PR's latest processing state. Completed requires the latest processing attempt to finish with a matching persisted completion receipt at the latest verified open PR head. The separate reviewed gauge counts any verified completion at that head, including one preceding a failed feedback retry. Worker success plus `REVIEWED` output must be corroborated by a submitted GitHub review from the configured owner at that head after the attempt started. Dry runs and launch-time `.reviewed` markers are insufficient. Existing logs can be imported only with the same GitHub verification. Counts are unique PR gauges, not attempt totals. Queued/running/completed/failed/blocked/missing partition the eligible set. A same-head feedback retry can be running or failed while reviewed still counts its earlier verified review; do not add reviewed to that partition. `completed_unique_heads` is a durable count of unique PR/head completion receipts; retries replace the same receipt key. Current-head metrics are as of the recorded verification time, not a claim of continuous GitHub observation.

The independent `launchd/com.llm-brain.review-watch.plist` template invokes `bin/review-watch` every five minutes. It performs read-only GitHub checks and sends fixed review-health transitions through the Hub's existing paired Telegram bot. Set `pr_review.monitoring.expected: true` only when review automation is authorized to run. The default is false; global/local pause and disabled reviews suppress alert delivery. No watchdog or review scheduler is installed automatically. Both must be installed separately after approval: a missing review scheduler cannot alert through a watchdog that is also stopped. The watchdog never launches workers or changes gates.

When armed, the watchdog detects an absent launchd review service, a heartbeat older than 900 seconds, discovery failure, an eligible item without processing for 900 seconds, dead workers and no log progress for 1,800 seconds. Thresholds live under `pr_review.monitoring`. A fresh capacity wait or explicit budget-stop is an expected wait, represented in metrics without a stuck/missing alert. New-head work resets its wait age. API verification errors block completion accounting and raise a verification incident. Alert state persists across restarts; unchanged successfully delivered incidents remain quiet, and resolved incidents send one recovery transition. Failed delivery is recorded per incident in metrics and retried with a five-minute exponential backoff capped at one hour; a failure does not block other incidents. Telegram has no idempotency key, so an ambiguous timeout after remote delivery may produce a duplicate on retry. A heartbeat/progress threshold reports lack of evidence, not proof of a code deadlock.

The Hub now needs a build and controlled restart to provide `POST /api/reviews/alert`. It reads the already-configured `telegram_token`, `telegram_chat` and `telegram_user` settings server-side; neither CLI metrics nor API callers receive credentials. The endpoint accepts only predefined incident names and a boolean transition, enforces the existing tailnet/same-origin checks, and sends generic messages to the paired owner chat. Preserve the deployed Hub's existing integration branch when incorporating this change; do not replace newer deployed Hub features with an older main build. Deploy the Hub adapter before arming the watchdog. Review and watchdog services remain opt-in, and the general issue/babysitter scheduler must stay stopped.
